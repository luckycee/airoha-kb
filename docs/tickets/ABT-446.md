!image-2024-09-04-19-54-59-981.png|width=707,height=228[图片: 

以下回覆客戶的問題:

1. Packet Error Rate解析 为什么从35信道到54信道没有数据？是否时我们软件设置，是否能修改？

channel的選擇是手機決定, 耳機只能透過LMP的機制掃描channel 0~79, 依照受干擾情形打分數, 提供手機參考, 最終的決定權還是在手機, 我目前無法從提供的資料得知為何手機不選channel 35~54。 channel的品質受環境干擾, RF硬體元件...等影響, 而耳機打分數的機制是類似Rssi值的計算方式, 透過硬體量測channel訊號強度給分建議手機, 我必須有airlog跟syslog才能知道當時我們是否給分上有偏見誤導手機選擇。

2. 我们看到C137/VR3000多工作在2-DH5，但是对标品牌的A20多工作在2-DH3，请帮忙分析下两个有什么差异？ 是否能修改？

音樂封包大小的決定是建立連線時我們會告訴手機A2DP layer參數 MTU (Media time unit), 手機會被MTU限制在一個封包內可塞入的data量,  參數越小手機可能會因為數據塞不下一個封包內而拆分成多個封包, 因此會使用2-DH3 packet type傳輸, 參數越大, 則可使用2-DH5傳輸, 不過要注意的是把封包拆分成多packet會更耗電且有因為拆分封包丟而造成其餘封包一起被丟的風險。

如果客戶認為封包更大會因為channel coherence time 小造成bit error rate 增加, 使封包因為CRC error被丟包, 我個人是覺得不會差距這麼大, 因為當初在選channel時, 就已經避免channel quality差的channel, 經驗上除非是特別髒的環境否則2-DH3跟2-DH5 CRC error的比例應該不會差太多。

3. 客户测试到Sleep A20的时隙周期为25ms，而[客户K]公司生产的三款产品的时隙周期为3.75 ms,请帮忙解答下这部分是否有影响？是否能修改？

這部分我猜客戶的 "时隙周期" 是指retransmission 時packet的時間間距, 如下圖所示, packet的retransmission時間點是手機決定, 耳機只能依照手機打包的時間點去收包, 沒辦法決定手機什麼時候打包, "Sleep A20的时隙周期为25ms" 這時間間距不大像retransmission 的間距, 比較像正常打包的時間間距, 一般來說造成retransmission的原因除了收包失敗CRC error外, 耳機可能為了省電進入sleep mode, 打le Adv封包...等, 造成沒法立即收包, 這部分我同樣需要airlog與syslog知道客戶指的事情是甚麼? 

傳統bluetooth BR/EDR在音樂封包傳書與接收上不會有固定的timing->anchor point, 我們只能猜測對方會在哪個時間點傳輸, 所以重點還是手機端的行為決定。

GCS的運作機制是透過耳機逐步掃channel 0~79 Rssi 值, 也就是channel signal強度, 由於WiFi channel bandwidth可為20MHz/40MHz/80MHz (Bluetooth一個channel bandwidth為1MHz), 所以當掃到channel 當下Rssi值與過去背景環境平均Rssi值差異大時, 我們就會屏蔽以這個channel為中心一定範圍內的channel, 並利用LMP channel classification建議手機可以傳輸訊號的channel有哪些, 來規避WiFi訊號。

Pixel手機在我們經驗上有時候他傳packet前半段時 RF訊號一開始會很強, 但到packet後半段時RF 訊號又會降低, 因為我們耳機接收端RF Power Amplifier必須依照packet訊號強度設定, 訊號小時功率就必須調大, 反之, 訊號大時功率就要調小, 所以有時候耳機端會因為來不及調整功率造成packet接收失敗, 這也是為甚麼我們會建議提供airlog確認是不是硬體上的問題, thanks
